# Backend loading audit

Audit date: 2026-11-09. The application targets NEAR testnet.

## Page loading flows

| Page | Source and load sequence | Current behavior and remaining cost |
| --- | --- | --- |
| Overview | `OverviewRegistryView` reads paginated NEAR `get_tokens` and `get_history_events` in parallel. `MyCommitmentsPreview` filters the creator's commitments from the event list, reads each matching commitment, then reads its token. | Counts are derived from the full token and event collections, so the overview reads every page. The page uses the shared five-second read cache and reports errors separately from an empty registry. |
| Discover | Browser calls `/api/meme-cooking/meme` without HTTP caching. The route reads the Supabase token snapshot and its synchronization metadata; a snapshot within the 15-minute freshness window is returned as a sync snapshot, otherwise Meme.Cooking is queried directly. A last-known-good nonempty response is retained for stale fallback. Browser separately reads all registry token pages to mark listings registered by exact testnet contract identity. | Provider pagination is sequential because each next-page URL comes from the preceding response. Registry token pages are sequential for the same cursor reason. Search and launch filtering are local and do not refetch. The route and upstream fetch use no-store, so a direct upstream response is actually fetched for each request rather than served from the app's 60-second/SWR cache. |
| My Commitments | Reads all paginated history events, selects `commitment_created` events by connected creator, hydrates those commitments, and reads their token identities. | The contract exposes no creator-indexed commitment view, so history must be scanned. Only the creator's matching commitment and token records are hydrated. |
| Commitment detail / token passport | Reads the token, scans paginated history to find commitments for that token, then loads each commitment's versions and evidence in parallel. Reviews are read per evidence; disputes are read for each commitment and evidence; resolved disputes also read their resolution. | This is the largest detail-page fanout. Related record collections are paginated but fully traversed for the selected token. The client limits concurrent hydration to six. The contract does not expose a single indexed passport view. |
| Evidence | In parallel, the commitment selector reads all commitments and their token records; the evidence selector reads all evidence, then hydrates the referenced commitments and distinct token records. | Evidence choices are currently unbounded at the page level. Commitment and evidence scans are paginated at the RPC boundary and cached, but the experience materializes all choices. |
| Reviews | Shares the all-commitment choice loader; for a selected evidence record, reads only that evidence's review pages. | Review loading is correctly scoped to selected evidence. Commitment choices still require a history scan. |
| Disputes | In parallel reads all disputes and all history events; also loads commitment and evidence choices for dispute targeting. Selecting a dispute reads its response and resolution together. | Initial choices and event history are unbounded scans. Detail reads are parallel, with explicit loading/error state. Expiry and resolver outcomes are described as dispute workflow state, not as commitment verdicts. |
| Activity | Reads the same full token and event collections as Overview; filters events in the browser. | The event filter does not reduce RPC reads. The contract currently offers cursor pagination but no server-side category filter or count view. |
| Profile | Uses wallet context and embeds `MyCommitmentsView` when connected. | Commitment reads follow the My Commitments flow; no separate profile backend source. |
| Passport directory | Reads every paginated `get_tokens` page from the NEAR testnet registry. | The directory currently materializes the full registry and has no client pagination. |
| Market detail | `/api/market-data/meme/[id]` reads the Meme.Cooking token and queries GeckoTerminal / DEX Screener where the NEAR contract identity and provider support permit. | Market snapshots and scheduled refreshes are stored in Supabase by the synchronization worker; unavailable providers are represented as unavailable, not zero market data. |

## Shared request safeguards

- Registry reads use the configured HTTPS testnet RPC and a testnet-only fallback. Read calls have bounded timeout/retry behavior, identical in-flight calls are deduplicated, successful views are briefly cached, and successful wallet writes invalidate the view cache. Failed reads are not cached as successful data. Signed transactions are not retried.
- Higher-level registry list helpers cache in-flight and successful paginated reads for five seconds, remove failed entries, and expose explicit invalidation after state changes. Fanout hydration uses bounded concurrency.
- Discovery accepts the provider's `meme_id` or `id` identifier, validates response and pagination shapes, constrains pagination URLs to the Meme.Cooking API host/path, and deduplicates by listing ID. A stale Supabase snapshot or last-known-good listing is labeled stale; an upstream failure without usable cached records remains an error.
- Supabase synchronization reads use server-only service credentials, bounded REST reads (1,000 rows per request), batched upserts, a database refresh lock, retry scheduling, and preserve prior successful market payloads on failed refreshes. Public Discovery reads only the selected listing snapshot; market refresh is separate.

## Findings and limits

The main measurable source of excess work is full-history scanning: Overview and Activity need it for counts and event history, creator commitments need it because the contract has no creator index, and token passports need it because the contract has no token-to-commitment index. The detail page then makes related evidence, review, dispute, and version reads. These are separate query paths rather than one shared slow request. Existing changes parallelize independent requests, deduplicate identical reads, bound fanout, and keep UI errors distinct from empty results.

The Meme.Cooking code path had a response-shape compatibility gap: records using `id` instead of `meme_id` were discarded by the browser normalizer. The normalizer now maps either field to `meme_id`, with regression coverage. The response path also validates malformed JSON and pagination. The API route and upstream fetch now bypass persistent HTTP/framework caches; only sync snapshots and explicitly marked last-known-good data can be reused. A live request to the upstream API could not be verified from this environment, so current provider availability and HTTP status remain unconfirmed; this report does not attribute a live outage to Meme.Cooking.

No before/after request trace or production timings were available during this audit. The current repository tests validate cache reuse, deduplication, pagination, stale fallback, and retry behavior, but they do not establish live latency gains. The most useful future contract-level optimization would be indexed/paginated views for creator and token commitments and event counts; adding those would change contract behavior and is outside this UI/data-loading pass.

## Vercel readiness

The app is a Next.js workspace at `apps/web`; the root npm build delegates to that workspace, and `next.config.ts` uses defaults. The sync route explicitly uses the Node.js runtime and a 60-second maximum duration. The contract and all browser registry reads remain configured for NEAR testnet.

At audit time, neither root nor app has a `.vercel` link, and no Vercel CLI executable is available in the environment. Production environment variables and linked project identity therefore could not be inspected, and no deployment was attempted. Required server-side deployment values include Supabase URL/service role key and cron secret when sync is enabled; public configuration includes the NEAR testnet RPC/network and registry contract ID. Secret values must be entered through Vercel settings and were not read into this report. Do not set a mainnet network or contract.
